# tgproxy-panel — план проекта

Веб-панель + Telegram-бот для управления пользователями существующего
[`tproxy-server`](https://github.com/telegramdesktop/tproxy-server) (WEB proxy для Telegram).
Прокси-сервер уже установлен через `deploy/install.sh`, домен и сертификат готовы. Эта система
только **выдаёт/отзывает секреты пользователям**, не трогает саму логику tproxy-server/MTProxy.

---

## 1. Контекст: как на самом деле работает tproxy-server (важно!)

Это критично понимать при реализации — **панель не редактирует Caddyfile на каждого пользователя**.

- Caddy слушает 80/443 и проксирует **весь** трафик на `127.0.0.1:8080` (relay). Caddyfile
  редактируется **один раз при установке панели** (см. раздел 6), а не на каждого юзера.
- Пользователи с их секретами живут в `/etc/tproxy-server/profiles.json` — список профилей вида:

  ```json
  {
    "profiles": [
      {
        "name": "user_123456789",
        "secret": "0123456789abcdef0123456789abcdef",
        "backend": "127.0.0.1:2398",
        "carrier_mode": "https"
      }
    ]
  }
  ```

  Один и тот же `backend` (127.0.0.1:2398, официальный MTProxy) можно шарить между всеми
  профилями — новый MTProxy-процесс на пользователя не нужен.
- Файл `profiles.json` должен иметь права `0400`, загружается через systemd `LoadCredential`
  (это подтверждено — установка была через `install.sh`).
- **Изменение профилей требует `systemctl restart tproxy-server`, и рестарт рвёт все активные
  сессии всех пользователей.** Живого релоада нет. Решено: выдаём/отзываем — рестартуем сразу
  (подтверждено пользователем, на масштабе ~50 юзеров это ок).
- `config.json` (глобальные лимиты процесса) панель не трогает.

**Важно для реализации:** прежде чем писать код записи `profiles.json` и патчинга Caddyfile,
Claude Code должен открыть реальные `deploy/Caddyfile`, `config.example.json` и
`profiles.example.json` из репозитория `telegramdesktop/tproxy-server` (и, если есть доступ —
реальные файлы на сервере пользователя), чтобы не гадать точный синтаксис.

## 2. Архитектура

```
                         ┌─────────────────────────────┐
Интернет :80/:443 ─────▶ │            Caddy             │
                         │  proxy.example.com           │
                         │                               │
                         │  path == /<RANDOM20>/*  ──────┼──▶ 127.0.0.1:9000  (панель, HTTP API + статика)
                         │  всё остальное          ──────┼──▶ 127.0.0.1:8080  (tproxy relay, как было)
                         └─────────────────────────────┘

tgproxy-panel (один Go-бинарник, systemd-сервис):
  ├─ HTTP-сервер (панель: логин, список юзеров, карточка, настройки)
  ├─ Telegram-бот (long polling, в том же процессе, отдельная goroutine)
  ├─ SQLite (данные о пользователях/заявках)
  └─ Модуль "applier": пишет profiles.json, делает бэкап, дёргает systemctl restart
```

Панель находится **на том же домене**, но по секретному пути (20 случайных символов),
сгенерированному один раз при установке — отдельный сабдомен/сертификат не нужен.

## 3. Стек

- **Язык:** Go (единообразно с самим tproxy-server, один статический бинарник, без Docker).
- **БД:** SQLite (`modernc.org/sqlite` — чистый Go, без cgo, проще собирать/переносить).
- **Telegram-бот:** long polling, библиотека — `go-telegram-bot-api/telegram-bot-api` или
  `mymmrac/telego` (на усмотрение Claude Code, любая с поддержкой inline-кнопок).
- **HTTP-роутинг:** `net/http` + `chi` (лёгкий, без лишних зависимостей).
- **Фронтенд панели:** без Node/npm-сборки — Go-шаблоны (`html/template`) + htmx +
  Tailwind (через CDN или один vendored css-файл) для SPA-подобного поведения без билд-пайплайна.
  Ассеты встраиваются в бинарник через `go:embed`. Использовать принципы из скилла
  `frontend-design` для непошаблонного, живого дизайна (не дефолтный bootstrap-вид).
- **QR-коды:** `skip2/go-qrcode` или аналог.
- **Только systemd**, без Docker, как и просили.

## 4. Модель данных (SQLite)

```sql
CREATE TABLE users (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  telegram_id   INTEGER UNIQUE NOT NULL,
  username      TEXT,
  first_name    TEXT,
  last_name     TEXT,
  status        TEXT NOT NULL CHECK(status IN ('pending','active','revoked','denied')),
  profile_name  TEXT UNIQUE,      -- имя профиля в profiles.json
  secret        TEXT UNIQUE,      -- 32 hex символа
  requested_at  DATETIME,
  issued_at     DATETIME,
  revoked_at    DATETIME
);

CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value TEXT
);
-- settings: auto_issue = "true"/"false"
```

Один пользователь — один активный профиль (проверять уникальность перед выдачей: если у
`telegram_id` уже есть запись со статусом `active`, повторный запрос в боте просто показывает
существующую ссылку/QR, новый профиль не создаётся).

## 5. Функциональность панели

**Авторизация**
- Логин/пароль захардкожены в `.env` (`ADMIN_LOGIN`, `ADMIN_PASSWORD` — хранить как bcrypt-хэш,
  даже если исходно вводятся плейнтекстом при установке).
- Сессия — подписанная cookie (HMAC на секретном ключе из `.env`), таймаут сессии, кнопка "Выход".
- Базовый rate-limit на попытки логина (защита от брутфорса, т.к. IP-ограничения не делаем).

**Список пользователей**
- Колонки: Telegram ID, имя (first+last / username), статус (pending/active/revoked/denied),
  дата запроса, дата выдачи.
- Сортировка по любой колонке (клик по заголовку).
- Живой поиск (input с debounce) по любому полю сразу при вводе, без перезагрузки страницы.
- Список заявок, ожидающих подтверждения (status=pending), визуально выделен/отдельная вкладка.

**Карточка пользователя** (открывается по клику на имя/ID)
- Полная информация: Telegram ID, username, имя, статус, даты.
- Секрет, готовая ссылка `https://t.me/webproxy?server=<host>&secret=<secret>`, QR-код.
- Кнопка "Скопировать ссылку".
- Кнопка "Отправить пользователю в Telegram" (бот шлёт юзеру сообщение со ссылкой/QR).
- Кнопка "Отозвать прокси" (revoke: убрать профиль из `profiles.json`, бэкап, рестарт,
  статус → `revoked`).
- Для pending-заявок — кнопки "Одобрить" / "Отклонить".

**Настройки**
- Тумблер: автоматически выдавать прокси при запросе / требовать подтверждение админа.
- Информация о последних бэкапах (список файлов в `/backup`, с датами).

## 6. Функциональность бота

- `/start` → приветствие + inline-кнопка "🔑 Получить прокси".
- Нажатие кнопки:
  - Если у юзера уже есть активный профиль → сразу показать существующую ссылку + QR
    ("У вас уже есть прокси: ...").
  - Если авто-выдача включена и активного профиля нет → сгенерировать секрет, записать в БД
    (status=active), применить в `profiles.json` (бэкап + рестарт tproxy-server), отправить
    ссылку + QR пользователю.
  - Если авто-выдача выключена → создать заявку (status=pending), сообщить юзеру "заявка на
    рассмотрении", отправить админу в Telegram уведомление с inline-кнопками
    "✅ Одобрить" / "❌ Отклонить" (плюс заявка появляется в панели).
- Обработка одобрения/отклонения из бота (по кнопкам у админа) — та же логика выдачи/отказа,
  что и в панели.
- Красивое оформление сообщений: эмодзи-иконки, `MarkdownV2`/HTML-форматирование, инлайн-клавиатуры.
  Свериться со скиллом `frontend-design` по общим принципам, адаптировать под текст/эмодзи-язык бота.

## 7. Модуль применения изменений ("applier")

Общий поток для выдачи/отзыва:

1. Прочитать текущий `/etc/tproxy-server/profiles.json`.
2. Скопировать его в `<INSTALL_DIR>/backup/profiles.json.<UTC-таймштамп>.bak`.
3. Хранить только последние **100** бэкапов (при превышении — удалять старые по времени).
4. Добавить/удалить профиль, провалидировать итоговый JSON (валидный JSON + уникальность
   `name`/`secret`).
5. Атомарно записать новый файл (temp-файл + rename), выставить владельца/права как у оригинала
   (`0400`, тот же владелец).
6. `systemctl restart tproxy-server`, дождаться `active` статуса (проверить через
   `systemctl is-active`, и опционально `curl 127.0.0.1:8081/readyz`).
7. Залогировать факт операции (без самого секрета в логах) в БД/аудит-лог.

**Права доступа.** Панели нужно писать в `/etc/tproxy-server/profiles.json` (root-owned, 0400)
и рестартовать системный сервис — это привилегированные операции. Рекомендуемый безопасный
вариант (вместо запуска всей панели от root):

- Панель работает от отдельного системного пользователя (`tgproxy-panel`).
- Есть небольшой root-owned скрипт-обёртка, например
  `/opt/tgproxy-panel/bin/apply-profiles.sh`, который делает шаги 2–6 из списка выше.
- В `/etc/sudoers.d/tgproxy-panel` — узкое правило `NOPASSWD`, разрешающее пользователю
  `tgproxy-panel` запускать **только** этот конкретный скрипт.
- Панель вызывает `sudo /opt/tgproxy-panel/bin/apply-profiles.sh <путь-к-новому-json>`.

(Простой альтернативный вариант — запускать весь сервис панели от root; проще, но хуже с точки
зрения безопасности. Claude Code реализует sudoers-вариант по умолчанию, но можно оставить флаг
для упрощённого root-режима.)

## 8. Установка (install.sh)

Скрипт в духе `deploy/install.sh` из tproxy-server:

1. Спросить путь установки (по умолчанию `/opt/tgproxy-panel`, можно указать свой).
2. Спросить/проверить путь к `profiles.json` и `config.json` tproxy-server (по умолчанию
   `/etc/tproxy-server/...`, с автоопределением, если сервис найден через systemd).
3. Спросить hostname прокси (например `proxy.example.com`) — тот же домен, что уже настроен.
4. Спросить токен Telegram-бота, Telegram ID админа (для уведомлений о заявках).
5. Спросить логин/пароль админа для панели → сохранить в `.env` (пароль — bcrypt-хэш).
6. Сгенерировать случайный path-токен (20 символов, `[a-zA-Z0-9]`) для URL панели.
7. Забэкапить `/etc/caddy/Caddyfile` в `<INSTALL_DIR>/backup/Caddyfile.<таймштамп>.bak`.
8. Вставить в существующий сайт-блок Caddyfile маршрут на путь-токен **выше** общего
   catch-all-проксирования на relay, например (уточнить точный синтаксис по реальному
   Caddyfile перед реализацией):

   ```caddyfile
   proxy.example.com {
       handle /<RANDOM20>/* {
           reverse_proxy 127.0.0.1:9000
       }
       handle {
           reverse_proxy 127.0.0.1:8080 {
               transport http {
                   response_header_timeout 40s
               }
           }
       }
       encode zstd gzip
   }
   ```

9. `caddy validate` перед применением, затем `systemctl reload caddy`. Если валидация не прошла —
   откатить бэкап, ничего не ломать.
10. Создать systemd unit `tgproxy-panel.service` (сам бинарник, HTTP на 127.0.0.1:9000 + бот
    внутри одного процесса), `sudoers.d`-файл и root-скрипт из раздела 7.
11. `systemctl enable --now tgproxy-panel`.
12. В конце вывести админу: полный URL панели (`https://proxy.example.com/<RANDOM20>/`) и
    напоминание про логин/пароль.

## 9. Конфигурация (`.env` / config-файл)

```
PANEL_PORT=9000
PANEL_PATH_TOKEN=<random20>
ADMIN_LOGIN=...
ADMIN_PASSWORD_HASH=...
SESSION_SECRET=<random>
BOT_TOKEN=...
ADMIN_TELEGRAM_ID=...
AUTO_ISSUE=false

TPROXY_HOSTNAME=proxy.example.com
TPROXY_SERVICE_NAME=tproxy-server
TPROXY_PROFILES_PATH=/etc/tproxy-server/profiles.json
TPROXY_CONFIG_PATH=/etc/tproxy-server/config.json
CADDYFILE_PATH=/etc/caddy/Caddyfile

DB_PATH=/opt/tgproxy-panel/data/panel.db
BACKUP_DIR=/opt/tgproxy-panel/backup
BACKUP_KEEP=100
```

`AUTO_ISSUE` дублируется в таблице `settings` — значение из `.env` используется только как
дефолт при первом запуске, дальше редактируется через панель.

## 11. Открытые технические риски для Claude Code — проверить в начале работы

- Точный синтаксис реально сгенерированного `deploy/Caddyfile` (там могут быть доп. директивы
  `timeouts`, TLS-настройки и т.д.) — прочитать файл из репозитория/с сервера перед написанием
  патчера, не полагаться только на пример из README.
- Точный владелец/группа `/etc/tproxy-server/profiles.json` на установленной системе (root:root
  ожидаемо, но лучше проверить `stat` на сервере) — от этого зависит, что именно должен делать
  root-скрипт apply-profiles.sh с правами файла после записи.
- Способ проверки готовности tproxy-server после рестарта — `systemctl is-active` +
  `curl --fail http://127.0.0.1:8081/readyz` (порт из README), с таймаутом и понятной ошибкой в
  панели/боте, если сервис не поднялся (в этом случае — не менять статус пользователя на
  `active`/`revoked`, откатить profiles.json из бэкапа).

## 12. Репозиторий и дистрибуция

Проект публикуется как публичный репозиторий:
**https://github.com/barakov-dot/tgproxy-panel**

Установка на целевой сервер должна происходить так же, как у самого tproxy-server —
`git clone`/`curl` + запуск `install.sh` из репозитория, без ручной сборки на сервере
(на сервере может не быть Go).

**Требования к репозиторию:**
- Структура в духе tproxy-server: `cmd/tgproxy-panel/`, `internal/...`, `deploy/install.sh`,
  `deploy/tgproxy-panel.service`, `deploy/apply-profiles.sh`, `.env.example`, `README.md`.
- `README.md` с инструкцией установки в стиле README tproxy-server (шаги, требования,
  проверка после установки).
- **GitHub Actions workflow** (`.github/workflows/release.yml`): при пуше тега `vX.Y.Z`
  собирать бинарник под `linux/amd64` (сервер — Debian 13 / Ubuntu 24, x86_64) и прикладывать
  его к GitHub Release. Это снимает необходимость иметь Go на целевом сервере: `install.sh`
  может просто скачать готовый бинарник с последнего релиза (`curl -L .../releases/latest/download/tgproxy-panel-linux-amd64`),
  либо, как fallback, собрать из исходников, если Go на сервере есть.
- `install.sh` в репозитории должен сам клонировать/обновлять код (или скачивать релизный
  бинарник) — то есть пользователь на сервере выполняет условно:
  ```bash
  git clone https://github.com/barakov-dot/tgproxy-panel.git
  cd tgproxy-panel
  sudo ./deploy/install.sh
  ```
  либо однострочник через `curl | bash` (если решите делать такой вариант — предупредить в
  README о рисках такого способа, дать и безопасную alternative-инструкцию).
- `.gitignore`: исключить `.env`, `data/*.db`, `backup/*`, скомпилированный бинарник.
- Раз репозиторий публичный — **нигде в коде и в примерах не должно быть реальных секретов**,
  токена бота, логина/пароля админа; только `.env.example` с плейсхолдерами.

**Кросс-платформенная разработка (Mac → Debian 13 / Ubuntu 24):**
- Разработка ведётся на macOS, эксплуатация — на Linux x86_64. Go отлично кросс-компилируется,
  специальных ухищрений не требуется, но нужно явно задавать таргет при сборке:
  ```bash
  GOOS=linux GOARCH=amd64 go build -trimpath -o tgproxy-panel ./cmd/tgproxy-panel
  ```
- БД-драйвер должен быть чистым Go без cgo (`modernc.org/sqlite`, а не `mattn/go-sqlite3`) —
  иначе кросс-компиляция с Mac на Linux потребует cgo-тулчейн/докер для линковки под нужную
  платформу, чего мы просили избежать.
- Локально на Mac для разработки/тестов собирать под `darwin/arm64` или `darwin/amd64` как
  обычно (`go build ./...`, `go test ./...`), под Linux — только для финального артефакта
  (вручную или через CI, см. выше).
- В `install.sh` и systemd-юнитах никаких предположений о macOS — они выполняются только на
  целевом Debian/Ubuntu сервере.

## 13. Итоговые решения (зафиксировано с пользователем)

| Вопрос | Решение |
|---|---|
| Стек | Go |
| Бот | long polling |
| Применение изменений | сразу рестарт tproxy-server на каждую операцию |
| Установка tproxy-server | через `deploy/install.sh`, стандартный layout |
| Масштаб | ~50 пользователей |
| Отзыв прокси | нужен |
| Заявка в боте | кнопка "получить прокси"; если уже есть — показывает существующий; уведомление админу — да |
| Расположение панели | тот же домен, путь = случайные 20 символов, дальше проксируется на :9000 |
| Защита панели | логин/пароль в `.env`, без доп. IP-ограничений/2FA |
| Бэкапы | с таймштампом перед каждым изменением, ротация — последние 100 |
| Репозиторий | публичный, https://github.com/barakov-dot/tgproxy-panel, установка через `install.sh` из репо |
